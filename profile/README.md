<h2>一、长期账号的四个特征，先看自己中了几条</h2>

<p>第一，账号注册满三个月以上且没有中断；第二，有付费订阅或长期使用记录；第三，登录地点相对固定；第四，账号背后有实际产出，丢了要重新积累。四条里中三条以上，固定出口的溢价就值得付；只中一条，共享池足够用。</p>

<h2>二、订阅主号：出口要固定，而且越少动越好</h2>

<p>付费账号的核心风险不在速度，在"变"。支付环节对地址变化的容忍度最低，前后两次登录跳了城市，可能只是多一次验证，也可能直接失败。所以这条线一旦跑通就不要动，能不动就不动，连服务商促销换套餐都要谨慎。</p>

<h3>固定出口的代价要提前认</h3>

<p>代价有三：一是成本高，独享按月付费不打折；二是灵活性差，地址出问题只能等替换；三是迁移麻烦，换服务商意味着重新养一段时间的记录。能接受这三条，再谈购买。接受不了，就退回共享静态，把预期调低。</p>

<h2>三、日常辅号：按角色分池，不要挤一条线</h2>

<p>辅号通常是查资料、试功能、跑对比用的，重要度低但数量多。合理排法是按角色分两到三个池：查询类共用一条共享静态，测试类用动态按量，互不干扰。这样任一条出问题，最多影响一个池，不会连累主号。</p>

<h3>分组命名这件小事为什么值得较真</h3>

<p>分组时给每个池起可读的名字，比如 query-pool、test-pool，配置里也用同名变量，避免半年后自己都分不清哪条线对应哪个账号。这条建议听起来琐碎，但真出事时能省掉大量回忆时间。</p>

<h2>四、短期项目：动态按量才是正解</h2>

<p>只跑两三周的项目，买独享月付是浪费。动态住宅按 GB 计费，用完即停，成本随用量走。要注意的是会话保持：动态池默认可能每次请求换地址，做需要连续会话的任务时，选支持 sticky 会话的套餐，窗口设十五到三十分钟。</p>

<h3>什么信号说明该从动态切到静态</h3>

<p>出现这三种情况就该切：同一个账号一周内被要求验证三次以上；任务从短期变成长期；开始涉及支付。三者出现任意一条，说明你在用不适合的工具干长期活，早换早省心。</p>

<h2>五、不匹配时，最省钱的替代是什么</h2>

<p>如果账号用量很低，一个月登录不到十次，最省钱的做法其实是共享静态加严格的使用纪律：固定时间、固定设备、固定浏览器目录。纪律能替代一部分硬件投入。反过来，如果用量极高但全是只读查询，可以考虑把请求合并批处理，减少连接次数，比升级套餐更有效。</p>

<h2>常见问答</h2>

<h3>只有一个小号，也值得买独享吗？</h3>

<p>答：看它值不值钱。如果只是查资料，共享静态完全够；如果这个号承载订阅和长期记录，哪怕只有一个也值得上独享，因为损失的不是 IP 费用而是账号积累。</p>

<h3>固定出口会不会反而更危险？</h3>

<p>答：固定本身不是风险，异常的是"固定出口上出现不符合该出口的行为"。长期稳定的出口在正常使用下更符合真实用户形态，前提是设备、时区、语言这些也要跟着稳定。</p>

<h3>可以从共享静态升级到独享吗？</h3>

<p>答：可以，建议在同一个地区内换，减少地址跨区带来的记录断层。切换时先退出登录、清理站点数据，再在新出口重新登录一次，不要带旧会话漂移。</p>

<h3>预算有限时先砍哪一项？</h3>

<p>答：先砍并发和带宽，这两项在低频场景下用不满；再砍辅号的独享，改共享静态；最后才动主号。主号的出口是整个方案的地基，不建议先从这里省钱。</p>
